01 / 12

First, hold this model in your head.

LG Duel is not one program with one loop. It is two programs — client and server — sharing a small physics-and-combat vocabulary. The server decides what is true. The client makes that truth feel immediate and readable.

Client: “make it feel now”

  • Reads keyboard and mouse
  • Predicts your own movement immediately
  • Interpolates other players smoothly
  • Builds camera, models, HUD, audio and effects
  • Sends input intent, never final damage
⇄

Server: “decide what happened”

  • Accepts and validates commands
  • Runs movement and collision at 125 Hz
  • Traces shots and simulates projectiles
  • Owns health, cooldowns, scores and match state
  • Publishes authoritative snapshots
The central ruleIf a value can decide who wins — position, health, damage, hit registration, cooldowns, projectile state — the server owns it. The client may predict or decorate it, but cannot silently become the authority.

02 / 12

One trigger pull, end to end.

Trace this path whenever the codebase feels too large. Almost every gameplay feature is a variation on it.

1. SampleSDL events become held/pressed actions and mouse view angles.
2. CommandA UserCommand records intent: move, jump, attack, view, weapon.
3. PredictThe client immediately runs shared movement for the local player.
4. AuthorizeThe server consumes commands, moves players, resolves shots and projectiles.
5. SnapshotThe server sends truth plus the last command sequence it accepted.
6. PresentThe client reconciles, interpolates remotes and renders effects + HUD.
0 ms
You press fire.

The app captures attack intent without waiting for a server round trip. Mouse view updates at render-frame frequency; fixed ticks sample that latest view into commands.

same frame
A sequenced command leaves the client.

Commands can be bundled so a dropped UDP packet does not necessarily erase one input.

next tick
The server runs its ordered simulation.

Input → match state → movement → collision → combat → projectiles → snapshot. Order is gameplay behavior.

on reply
The client merges truth with responsiveness.

It drops acknowledged commands, resets to server state, replays the still-pending inputs, then presents the result.

src/server/ServerGame.cpp · ServerGame::tick
void ServerGame::tick(float fixedDt) {
  receivedCommandThisTick_.fill(false);
  receiveCommands();
  updateMatchState();
  updateBotCommands(fixedDt);
  // clear one-tick events and cooldowns…
  // move players, resolve collision, then combat…
  simulateRockets(fixedDt);
  // retain events, record history, publish snapshot…
}
Python reading: this is an ordinary method mutating the server object. The trailing underscore means “private member by convention,” not special syntax.
Why it matters: reordering calls changes the rules. A shot traces against positions produced earlier in this tick; snapshots describe the completed tick.
03 / 12

C++ for a Python-shaped brain.

You do not need to master the whole language before reading this project. Learn the handful of shapes that repeat in gameplay code.

struct ≈ dataclass

PlayerState and UserCommand are named bundles of typed fields. Unlike Python objects, their size and layout matter to memory and performance. Network compatibility comes from the explicit codec's field order — not native struct layout.

T& ≈ mutable object reference

simulateMovement(PlayerState& player, ...) edits the caller’s player. const T& borrows without copying and promises not to edit.

.hpp says what; .cpp says how

Start at the header for types and function signatures. Jump to the same-named implementation file when you need behavior.

std::array<T, N> is bounded

It is closer to a fixed-length typed list. Fixed capacity makes per-tick cost and packet size predictable — important in competitive code.

enum class is a strict choice

Weapon::Railgun and MovementMode::Airborne cannot be mixed with arbitrary integers without an explicit conversion.

Compilation catches contract drift

Change a function’s parameters and all callers must update. It is noisier than Python, but the errors form a to-do list across client, server and tests.

04 / 12

Movement is the game’s handwriting.

The player sends wishes; simulateMovement turns those wishes into velocity and a collision-safe position. Because the same function runs for prediction and authority, even a small asymmetry can become a visible correction.

1. Interpret intent in view space

Forward/strafe axes are rotated by yaw, producing a desired horizontal direction. This is why “W” follows where the player looks, not world +X. Jump, crouch, sneak and dash are carried as button state or edges.

UserCommand.hpp → Movement.cpp · simulateMovement

2. Accelerate under different rules

Ground friction slows coasting. Ground acceleration chases the desired speed. In air, acceleration and optional air control alter direction without giving the same grip. Freeze effects scale movement. Dash and flight have their own bounded state.

MovementTuning · movement cvars

3. Slide, step, and resolve

Movement sweeps the player bounds, clips velocity along collision planes, and retries a step-up path when grounded movement loses horizontal progress. Player/player collision is resolved on the server, followed by a final arena collision pass.

Collision.cpp · MovementTests.cpp

4. Preserve state across ticks

PlayerState holds grounded/airborne/flying mode, jump-held state, dash timers, knockback time and jumppad cooldown. These fields turn a stateless formula into a consistent movement machine.

Weapons ask three different questions.

Can it fire now? What did it touch? What consequences are allowed? The server answers all three, while shared combat helpers supply deterministic traces and weapon-specific calculations.

Permission

Is attack held? Is the player alive? Is the weapon selected and pulled out? Is cooldown zero? Is there ammo? Is the match live?

Geometry

Hitscan traces world + player cylinders immediately. Projectiles allocate a bounded slot, move each tick, and collide later.

Consequences

Apply allowed damage, impulse, self-damage scaling, vampirism, hit feedback, accuracy stats, frag and round state.

06 / 12

Networking hides delay without hiding truth.

There are three distinct techniques here. Mixing them up is the fastest way to make network code feel mystical.

Prediction

Who? Your local player.
How? Run movement immediately and remember the command.
Why? Input should not wait for ping.

Reconciliation

Who? Your local player.
How? Reset to server truth, discard acknowledged commands, replay the rest.
Why? Prediction must eventually agree.

Interpolation

Who? Remote players.
How? Render slightly behind, between buffered snapshots.
Why? UDP arrivals are uneven.

Snapshots carry authority

Player state, acknowledgements, match state, projectile/event arrays, accepted tuning, and a compact map descriptor/revision — not the arena geometry itself.

The map is both stage and rulebook.

A restricted TrenchBroom/Quake text map is parsed and converted into a fixed-capacity Arena on both server and client. The server replicates a compact name/hash/revision descriptor; the client loads the same local file, verifies its content hash, then builds cached world geometry.

.map textEntities, brushes, faces and material names.
ParseMapParser.cpp validates the supported authoring subset.
ConvertMapToArena.cpp creates walls, brushes, spawns, triggers and lights.
SimulateArena drives collision, traces, pickups and jumppads.
RenderRenderable geometry becomes a cached static world mesh.

Scale

40 TrenchBroom units = 1 LG Duel world unit. A 16-unit stair becomes 0.4 game units.

Playerclip

Collision-only brushes stay in Arena but set renderable=false. A clip ramp can make visible stairs move smoothly.

Verified locally

Arena geometry does not travel in snapshots. A descriptor/revision tells clients which local map to load, and the content hash prevents silently using different geometry.

Current limitation worth rememberingPlayerclip blocks players, hitscan and projectiles because collision content masks are not separated yet. A map geometry tweak can therefore change both navigation and weapon behavior.

10 / 12

Four changes you can make on purpose.

Each recipe starts at the narrowest safe surface, identifies the code path that consumes it, and names the tests that protect the result.

Good first change · low blast radius

Make ground acceleration feel snappier

  1. Edit g_accel in config/server_cvars.cfg.
  2. Run the server and compare starting and reversing acceleration at the same g_maxspeed. Stopping without input is chiefly g_friction + g_stopspeed.
  3. Read the early acceleration cases in MovementTests.cpp.
  4. A changed shipped default, behavior, range, storage, authority or user-visible meaning also requires tests and an update to CONSOLE-BIBLE.md.
Balance change · server authority

Change how quickly rockets cross a room

  1. Edit weapon.rl.speed in balance.cfg.
  2. Follow it through BalanceConfig into rocketLauncherTuning_.speed. Cooldowns are ticks: at 125 Hz, 100 ticks = 0.8 seconds.
  3. Do not compensate with a visual-only projectile offset; the server projectile position is truth.
  4. Run combat, server and projectile self-knockback tests; playtest leading and dodge windows.
Presentation change · client only

Make hit confirmation more readable

  1. Trace snapshot LocalHitFeedbackEvent into LocalHitFeedback.cpp and HitConfirmAudio.cpp.
  2. Adjust fade, layout, color or sound presentation — not damage application.
  3. Keep event IDs/retention in mind so packet loss or duplicates do not double-play feedback.
  4. Run local-hit-feedback, hit-confirm-audio, HUD and screen UI tests.
World feel · cross-domain

Smooth a staircase without changing its look

  1. Keep visible stair brushes in the map.
  2. Add a ramp brush covering the tops and apply common/playerclip to every face.
  3. Validate the map and test walking, jumping, hitscan and projectiles around it.
  4. Remember: current playerclip also blocks traces/projectiles, so confirm combat sightlines.

12 / 12

Words you will see everywhere.

Once these terms are precise, the code becomes much easier to discuss and change.

Tick / fixed timestep

One simulation step with a constant duration. LG Duel uses 125 per second, so each step is 0.008 seconds. Stable simulation time improves repeatability even when render frames vary.

Authority

The machine whose answer becomes truth. The server is authoritative for gameplay state; the client is authoritative only over its local input intent and presentation preferences.

Command / snapshot

A command travels client → server and describes intent. A snapshot travels server → client and describes authoritative state plus acknowledgements/events.

Prediction / reconciliation / interpolation

Prediction immediately estimates local movement. Reconciliation corrects that estimate using server truth and replay. Interpolation smooths remote state between buffered snapshots.

Hitscan / projectile

Hitscan traces a ray/shape and resolves immediately. A projectile has position and velocity across ticks, so future collision decides its result.

Cvar

A console variable: named runtime configuration with registration, validation, storage and user-facing meaning. It must also be documented in the console bible when changed.

Hot path

Code that runs frequently: every server tick, render frame or packet. Avoid unbounded work, filesystem access, noisy logging and hidden allocation here.

  • Can you state which side owns the new truth?
  • Did you preserve fixed-tick/prediction assumptions?
  • Did you choose the correct config lane?
  • Did protocol layout change?
  • Did you add/adjust the closest behavioral test?
