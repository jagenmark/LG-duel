Finding 1

One packet is carrying too many kinds of decisions.

CommandPacket started as the shape of player input. It now also carries runtime tuning, combat settings, chat, player names, readiness, resets, bot controls, and lag-comp timing.

The source fact

In src/net/NetProtocol.hpp, CommandPacket includes UserCommand, reset, ready, viewed server tick, movement tuning, player size, LG knockback, vampirism, chat, name, self-damage, health, and bot dodge fields.

Why it hurts

A weapon change can now involve input, networking, server settings, UI commands, and protocol encoding. The path is harder to reason about because unrelated concerns share one message.

The right direction

Keep the hot player command small. Put admin-style tuning and social actions behind clearer request shapes, even if they still share transport code for now.

Before and after mental model

Current shape

CommandPacket
  UserCommand
  requestReset
  toggleReady
  movementTuning
  combat tuning
  chat/name
  bot controls

One packet means many reasons to change the same API.

Safer shape

PlayerCommandPacket
  UserCommand
  viewedServerTick

GameControlRequest
  ready/reset/tuning/chat/name

The server can still process both, but ownership is clearer.

What to do next

Do not build a general engine message bus. First, rename or split the broad tuning path so ordinary per-tick input stays obvious. The useful test is simple: a future weapon change should not require mentally parsing chat, bot, health, and movement-tuning fields.
