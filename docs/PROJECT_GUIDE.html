This is a deliberately narrow C++20 game prototype: two native clients send input over UDP to a dedicated server, the server simulates a Quake-like duel at 125 ticks per second, and each client predicts itself while rendering server snapshots.

1. Orientation: what this project is

The design goal is not “build an FPS engine.” It is “make one 1v1 lightning-gun duel feel correct and measurable.” That focus explains the architecture: gameplay is plain data and functions, rendering is downstream of simulation, networking exposes prediction diagnostics, and tests exercise the simulation without opening a window.

ClientSamples keyboard/mouse, creates a numbered UserCommand, predicts local movement, and renders.
→
UDP + protocolSerializes redundant commands and snapshots into bounded, versioned packets.
↔
ServerOwns truth: movement, collision, hits, health, score, match phases, and snapshots.
The single most important rule: the server's ServerSnapshot is authoritative. The client's predicted player is a temporary low-latency estimate, and rendered remote state is an interpolation between snapshots.

Core executable

lg_duel_server runs the headless authoritative loop.

Playable executable

lg_duel_client needs SDL3 for window, input, audio, and rendering.

Testable core

lg_duel_core contains simulation, netcode, client prediction, console, and server logic with no renderer dependency.

2. Build, test, and run

Normal debug build

cd C:\Users\Samuel\.codex\worktrees\a187\LG-duel
cmake --preset default
cmake --build --preset default
ctest --preset default

The default preset uses Ninja, C++20, debug symbols, tests, and optional SDL3. If SDL3 is absent, everything still compiles but the client executable is only a message-printing skeleton.

Playable SDL3 build: easiest repository-supported route

The project can fetch its pinned SDL release itself. Configure from the repository root:

cmake --preset default \
  -DLG_DUEL_FETCH_SDL3=ON \
  -DLG_DUEL_REQUIRE_SDL3=ON
cmake --build --preset default
ctest --preset default

In PowerShell, either enter that on one line or use the backtick (`) rather than the Bash backslash for line continuation.

# PowerShell, one line
cmake --preset default -DLG_DUEL_FETCH_SDL3=ON -DLG_DUEL_REQUIRE_SDL3=ON

FETCH downloads/builds pinned SDL 3.4.10 when an installed package is not found. REQUIRE makes configuration fail instead of silently producing the non-playable skeleton. These options live in cmake/Dependencies.cmake.

Start a local duel

# Terminal 1
.\build\default\lg_duel_server.exe 27960

# Terminals 2 and 3
.\build\default\lg_duel_client.exe 127.0.0.1 27960
Toolchain consistency matters. C++ libraries must be built for the same compiler/runtime as the app. FetchContent avoids many “MSVC library with MinGW compiler” mismatches by compiling SDL as part of this build.

Fixed ticks versus rendered frames

Simulation advances in exact 8 ms increments because kFixedTickRate = 125. Rendering runs whenever the machine can draw a frame. planFixedTicks() accumulates real elapsed time and tells the client how many simulation steps to execute, capped at eight per frame. Excess complete ticks are dropped and instrumented to prevent a “spiral of death.”

// Conceptual Python equivalent
accumulator += max(0, elapsed)
available = floor(accumulator / fixed_dt)
ticks_to_run = min(available, 8)
dropped = available - ticks_to_run
accumulator -= available * fixed_dt

The server uses a different scheduler: it sleeps until the next 8 ms deadline and resets its deadline if it falls more than eight ticks behind.

Headers (.hpp) and implementations (.cpp)

A header declares the public shape—types and function signatures. A .cpp file defines behavior. For example, Movement.hpp says that simulateMovement exists; Movement.cpp contains its algorithm. CMake compiles each .cpp separately and links their object files.

Value semantics are intentional here

PlayerState, UserCommand, and ServerSnapshot are plain values. Assigning one normally copies its fields. This makes saved history, packet decoding, deterministic replay, and testing explicit. Large or shared runtime objects—transports and sessions—use references or unique_ptr instead.

Why declarations end in semicolons

Class, struct, and enum declarations end with ;. Function definitions do not. Names ending in _, such as snapshot_, are private member variables by project convention.

5. Gameplay simulation

The simulation layer is the best entry point because it is small, deterministic, and independent of SDL and sockets. Its core data types are Vec3, UserCommand, PlayerState, Arena, and weapon result structs.

Movement

Movement.cpp takes current state plus one command and mutates the player by exactly one fixed time step:

  1. Choose grounded/airborne or flying mode.
  2. Update view yaw and pitch.
  3. Apply jump edge detection (jumpHeld prevents repeated jumping).
  4. Apply ground friction when grounded.
  5. Build a desired direction from forward/right inputs and view yaw.
  6. Accelerate toward desired speed; optionally apply QuakeWorld-style air control.
  7. Apply gravity (or flight damping/thrust).
  8. Request the new position and resolve arena collision.
simulateMovement(player, command, arena, tuning, 1.0f / 125.0f);

Notice the absence of wall-clock access, rendering, random input, or globals. Given the same inputs and initial data, it should produce the same output.

Arena and collision

Arena.cpp constructs a Thunderstruck-inspired arena from 24 or fewer axis-aligned boxes. The same boxes serve four purposes: movement blocking, weapon occlusion, prediction, and rendering.

  • Players are vertical cylinders: radius plus half-height.
  • Arena walls are axis-aligned boxes with min/max corners.
  • resolvePlayerArenaCollision clamps world bounds, resolves floors/ceilings/walls, and supports 0.45-unit steps.
  • resolvePlayerCollision separates overlapping player cylinders and removes inward relative velocity.
This is purpose-built collision, not a general physics engine. That is consistent with the repository's narrow scope.

Combat

Combat.cpp contains reusable traces and the direct LG/railgun algorithms. ServerGame.cpp coordinates cooldowns, rockets, lag compensation, damage application, vampirism, scoring, and death.

WeaponMechanicDefaults in code
Lightning gunContinuous hitscan; fractional damage accumulates across ticks18 range, 80 DPS, 22 knockback/sec
RailgunSingle hitscan with cooldown100 range, 80 damage, 188 ticks cooldown
Rocket launcherServer-owned projectiles, direct/splash impact22.5 speed, 3 radius, 100 damage, 100 ticks cooldown

A hitscan trace first finds the nearest world obstruction, then tests the target cylinder only up to that distance. This is why cover blocks LG and rail shots.

Lag compensation

Each command includes the newest server tick the shooter had viewed. When a fresh attack command arrives, the server computes how far behind that view was and rewinds the target used for the hit test, capped at 25 ticks (200 ms). Damage and knockback are then applied to current authoritative state. History is a deque of 26 frames.

6. The authoritative server

ServerApp owns process-level concerns: create a UDP socket, read console input on a detached thread, schedule 125 Hz ticks, apply server cvars, and call ServerGame::tick. ServerGame owns gameplay.

One server tick, in order

  1. Drain and validate new commands by player and sequence.
  2. Advance the match phase and optional bot dodge commands.
  3. Clear transient events and decrement weapon cooldowns.
  4. Simulate movement for both alive players.
  5. Resolve player-player and arena collision.
  6. Copy player states for combat evaluation.
  7. For each attacker: gate attacks by match phase, rewind target history, simulate selected weapon.
  8. Apply damage and knockback to current authoritative players.
  9. Advance rockets and explosions.
  10. Update live timer, death/round/match transitions, and combat statistics.
  11. Increment server tick, record history, and publish one snapshot.

Match state machine

WaitingForPlayers → WaitingForReady → Countdown → Live → RoundEnd → Countdown

When a score reaches roundLimit, RoundEnd becomes MatchEnd; after its timer, scores/readiness reset. Losing required players returns the game to WaitingForPlayers.

Test constructor shortcut: ServerGame initially marks both players connected/ready and the phase live. A real ServerApp immediately replaces connection state from UdpServerTransport.

The network layer is split into three concerns: logical packet data, byte encoding, and delivery.

Protocol and codec

Protocol version 18 uses magic 0x4C474455, packet type, flags, payload size, and reserved fields in a 12-byte header. Packets are capped at 768 bytes. Integers and IEEE-754 floats are written explicitly in little-endian order; strings are length-prefixed and restricted to printable bytes.

Decoding checks magic, version, expected packet type, exact payload length, enum ranges, booleans, string lengths, player index, movement limits, and finite floating-point values. It does not serialize C++ structs by copying their memory, which avoids padding and ABI problems.

ServerSnapshot is intentionally comprehensive: two player states, acknowledgements, weapon events, rockets, score/match state, rules/tuning, stats, names, chat, and diagnostics.

UDP connection lifecycle

1. Requestclient nonce + protocol header
→
2. Acceptsame nonce + assigned slot + server tick
→
3. Play3-command redundant bundles ↔ snapshots
→
4. Healthtokenized ping/pong + 5 s timeout

UDP itself has no connections or guaranteed delivery. The project builds its own lightweight session semantics on top. Recent commands are bundled redundantly so losing one datagram does not necessarily lose that input forever. Sequence comparisons deliberately support 32-bit wraparound via signed subtraction.

8. Client prediction, reconciliation, and interpolation

Prediction

When the client sends a command, it immediately runs the same simulateMovement function locally and saves the command in pendingCommands_. The player responds without waiting for a network round trip.

Reconciliation

When a newer snapshot arrives:

  1. Discard pending commands at or before the server's acknowledgement.
  2. Replace predicted state with the authoritative local player state.
  3. Replay all still-pending commands through the shared movement function.
  4. Measure correction distance and increment diagnostics when it is non-trivial.
# Conceptual Python
pending = [cmd for cmd in pending if newer_than(cmd.sequence, ack)]
predicted = copy(authoritative)
for cmd in pending:
    simulate_movement(predicted, cmd, arena, tuning, fixed_dt)

Interpolation

The remote player is not predicted. The client keeps previous and current snapshots and linearly blends position/velocity using the fixed-tick accumulator. Angles use shortest-path wrapping. Discrete values such as health remain from the previous snapshot until the interpolation endpoint.

Prediction answers “where should I be now?” Interpolation answers “how do I display two known remote samples smoothly?” Reconciliation repairs prediction when server truth arrives.

9. SDL application shell

GameApp.cpp is the largest file because it is the integration boundary. It does not define authoritative gameplay, but it wires together many user-facing responsibilities:

Platform

SDL video/audio initialization, window lifetime, event polling, mouse modes.

Input

Bindings, console/chat text entry, mouse deltas, aim modes, command construction.

Client loop

Session updates, fixed ticks, command sequencing, prediction, interpolation alpha.

Presentation

HUD, scoreboard, hit feedback, generated audio cues, title diagnostics, render settings.

The SDL portion is guarded by #if LG_DUEL_HAS_SDL3. If CMake did not find/fetch SDL3, the compiler builds only the fallback message branch. This explains why the executable can compile successfully but not open a game window.

Frame-loop order

  1. Poll SDL events and update input/console/chat state.
  2. Update network session and runtime configuration.
  3. Measure elapsed time and plan up to eight fixed ticks.
  4. For each tick, build/send a command and predict local movement.
  5. Process audio events from authoritative snapshots.
  6. Calculate interpolation alpha and assemble render states.
  7. Render predicted local player, interpolated opponent, snapshot combat, HUD, and console.
  8. Update session once more and yield briefly with SDL_Delay(1).

LG_DUEL_RENDER_BACKEND=gpu requests SDL_GPU. It prefers Vulkan, then automatic GPU selection, then falls back to SDL_Renderer. The 3D path uses depth-tested opaque geometry, non-depth-writing translucent geometry, and a screen-space HUD pass.

Useful boundary: scene-building tests can inspect draw commands and vertices without creating a GPU device. Manual verification is still needed for actual backend output.

11. Console, cvars, and input bindings

ConsoleSystem is a small typed command registry. A cvar has a name, description, default value, flags, optional numeric range, and optional reference value. Its value is a std::variant<bool, int, float, string>.

  • Archive: write to client config.
  • ReadOnly: cannot be changed through normal commands.
  • Client: identifies client-side/requested settings.

InputBindings maps normalized key names to console commands. Button commands use paired press/release forms such as +forward and -forward. Releasing all bindings when opening the console prevents “stuck key” state.

Configuration uses SDL's platform preferences path and saves archived cvars plus binding lines to client.cfg. See CONSOLE-BIBLE.md for the full command reference.

Focused iteration

14. Recommended learning path

  1. Data first: read Math.hpp, UserCommand.hpp, PlayerState.hpp, and NetProtocol.hpp. Do not chase implementations yet.
  2. One pure system: read Movement.cpp beside MovementTests.cpp. Translate each test setup into “given/when/then.”
  3. Combat geometry: read Combat.cpp beside CombatTests.cpp.
  4. Server orchestration: trace ServerGame::tick top to bottom, using the numbered tick order in this guide.
  5. Prediction: read Prediction.cpp, then ClientGame.cpp. Manually track three numbered commands and one acknowledgement.
  6. Wire format: compare structs in NetProtocol.hpp with matching write/read functions in NetCodec.cpp.
  7. Real transport: read UdpTransport.cpp only after the logical protocol is clear.
  8. Platform integration: read the GameApp::run frame loop. Skip the long cvar and audio lists on the first pass.
  9. Rendering last: begin with DrawList2D.hpp and scene tests before the large backend implementation.
A productive exercise: add a small movement test that changes one tuning value and predicts the resulting velocity. This teaches compilation, value initialization, references, fixed-step math, and the test style without touching sockets or SDL.

Use the repository discipline: state a hypothesis, add or run a failing focused test, make the smallest change, run focused tests, then the whole suite. Do not move gameplay truth into rendering or use frame time in authoritative simulation.

16. Glossary

Authoritative

The version of state that ultimately wins disputes. Here, the server.

Tick

One discrete simulation step; 8 ms at 125 Hz.

Snapshot

A server-produced copy of world/match state sent to clients.

Prediction

Running local movement immediately before server confirmation.

Reconciliation

Resetting to server truth and replaying unacknowledged inputs.

Interpolation

Blending between two known snapshots for smooth presentation.

Hitscan

An instantaneous ray/shape trace rather than a traveling projectile.

Lag compensation

Testing a shot against historical target state visible to the shooter.

Cooldown

Tick count before a weapon may fire again.

cvar

Console variable: named, typed runtime configuration.

Translation unit

One .cpp plus included headers, compiled into one object file.

ABI

Binary compatibility rules; why SDL binaries must match the compiler/toolchain.
